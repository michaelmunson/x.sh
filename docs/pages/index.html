x.sh

A personal script manager and lightweight CLI app framework for your shell.

Install 
curl -fsSL https://raw.githubusercontent.com/michaelmunson/x.sh/main/install.sh | bash
Overview

x is a CLI that helps you create, organize, and run scripts across projects, as well as providing a framework for creating complex CLIs.

Overview

  • Script management: Store your favorite scripts globally in ~/.x.sh/scripts/, complete with descriptions, language info, and usage statistics.
  • Project automation: Define project-specific commands in ./x.yml files, enabling consistent development workflows with versioned, tracked, and portable automations.
  • App framework: Create fully-featured CLI apps using <name>.x.yml files. Describe options, arguments, and subcommands (in your shell language) in YAML . x.sh provides argument parsing, validation, and helpful error messages before any script runs.
Installation

Automated install (recommended)

The install script clones the repo, builds in release mode, and places the binary in ~/.local/bin/.

curl -fsSL https://raw.githubusercontent.com/michaelmunson/x.sh/main/install.sh | bash

Or download and run manually:

wget https://raw.githubusercontent.com/michaelmunson/x.sh/main/install.sh
bash install.sh

Requirements

  • Rust / Cargo: the script prompts you to install via rustup if missing.
  • Git: used to clone the repository (skipped if you run the script from inside the repo).
  • An internet connection for the initial clone and build.

What the script does

  1. Checks for Rust/Cargo.
  2. Clones github.com/michaelmunson/x.sh (or uses the current directory if already in the repo).
  3. Runs cargo build --release.
  4. Copies target/release/x to ~/.local/bin/x.
  5. Verifies the installation by running x --help.
PATH Ensure ~/.local/bin is on your PATH. Add export PATH="$HOME/.local/bin:$PATH" to ~/.bashrc, ~/.zshrc, or ~/.profile, then restart your shell.

Manual build

git clone https://github.com/michaelmunson/x.sh.git
cd x.sh
cargo build --release
# Binary at target/release/x: copy or symlink into your PATH

First-run directory layout

On first use, x creates ~/.x.sh/ with the following structure:

~/.x.sh/
├── scripts/          # your global script files
├── apps/             # global app YAML files (<name>.x.yml)
├── metadata/         # per-script TOML metadata
│   └── <name>.toml
├── config.json       # default_program and other settings
├── metadata.json     # usage / activity tracking
└── config/
    └── llm.sh        # LLM provider script (after x --config)
Quick Start

1. Create your first script

x --init hello-world
# or: x -i hello-world

Interactive prompts ask for the script name (alphanumeric + dashes), an optional description, and a programming language. Your $EDITOR opens so you can write the script body.

2. Run it

x hello-world
x hello-world arg1 arg2   # args pass through to the script

3. List installed scripts

x --ls
# or: x -l

Shows a formatted table with name, description, language, groups, and last-run timestamps.

4. Add to PATH (optional)

x --ln hello-world
# Now run directly: hello-world

5. Project-local commands (optional)

Drop an x.yml in your project root to define repo-specific tasks:

x.yml 
test: npm test
build: |
  npm run build
  echo "Built $1"   # $1 = first arg after 'build'
x test
x build v1.0.0
Architecture

Command resolution flow

When you invoke x <name> [args…], x walks a fixed resolution chain. The first match wins and the process exits after execution.

Local app discovery

Unlike x.yml (current directory only), local apps are discovered by walking from the current working directory up through every parent directory. The nearest <name>.x.yml wins. This lets monorepos keep a shared app at the repo root while you work in subdirectories.

Global script lookup

Scripts in ~/.x.sh/scripts/ are matched by exact filename first, then by basename without extension, so x c-test finds c-test.c automatically.

Metadata model

Each global script can have a companion TOML file at ~/.x.sh/metadata/<name>.toml:

description = "Fetch a URL with curl"
groups = ["network", "utils"]
program = "bash

Activity data (created, updated, last_executed) is stored separately in ~/.x.sh/metadata.json and shown in x --ls.

Inline script execution

Project-local x.yml entries and certain inline paths run via your configured default program (typically bash):

<program> -c '<script body>' x <remaining-args…>

Positional parameters in the script body ($1, $2, …) refer to arguments after the command name.

Script/App Resolution Order

When you run x <name> [args…], x walks a fixed resolution chain. The first match will be executed.

  1. ./x.yml → project-local inline script (CWD only)
  2. ./<name>.x.yml → local app (CWD, then parent dirs)
  3. ~/.x.sh/apps/ → global app
  4. ~/.x.sh/scripts/ → installed global script
Commands

x --init | -i [name] [script]

Create a new global script or re-open an existing one in your editor.

  • x -i: fully interactive (name, description, language, editor).
  • x -i my-script: prompts for metadata, opens editor. If the script exists, you can rename it first; metadata and history follow the new name.
  • x -i my-script "echo hello": creates the script with inline content using the default or existing program.
Note: Script names must be non-empty and contain only letters, numbers, and dashes.

x <script_name> [args…]

Execute a command using the resolution order described in Architecture. Arguments are forwarded verbatim.

x --ls / x -l

List all global scripts in a table with description, program, groups, and activity timestamps.

x --delete <name> / x -d

Remove a global script and its metadata. Does not remove symlinks created with x --ln; delete those separately.

x --ln <name> [link_name]

Symlink a script into ~/.local/bin/ so you can invoke it without the x prefix.

x --ln my-script          # → ~/.local/bin/my-script
x --ln my-script alias    # → ~/.local/bin/alias
x -d --ln my-script       # remove the symlink

x --src <name>

Print the absolute path of a script or app file. Resolution: local app → global app → global script. x.yml keys are not matched.

x -i --app [--local | --global] [<name>]

Create a new app YAML file. Scope flags control where the file is written; without them, x prompts interactively.

x --config

Interactive configuration for default script language and LLM provider. See the Configuration section.

Scripts
Global Scripts

Global scripts are plain files in ~/.x.sh/scripts/. Each script is executed with the program stored in its metadata (or the global default from x --config).

Creating and editing

x -i is the primary workflow. x opens your $EDITOR, and on save, writes the file and metadata.
Re-running x -i <name> on an existing script lets you edit in place or rename.

Passing arguments

# Script: curl-google (bash)
curl -s "https://google.com$1"

$ x curl-google /search
# → curl -s "https://google.com/search"

Program / interpreter

The program field in metadata determines how x invokes the file, such as bash, python, node, go run, etc. Set per-script during x -i or rely on the global default.

Groups

Metadata groups are free-form tags for organization. They appear in x --ls output to help you scan large script collections.

Symlinks vs scripts

x --ln creates a symlink in ~/.local/bin/, not a copy. The symlink points at the script file in ~/.x.sh/scripts/, so edits via x -i are reflected immediately.

Project-local Scripts

Place a file named x.yml in your current working directory. When you run x <name>, x loads it and looks for a top-level key matching <name>. If found, the entry runs; otherwise x falls back to global scripts.

Warning: Only the CWD is checked for x.yml, not parent directories. Invalid YAML fails immediately; x does not fall back to global scripts on parse errors.

String entries (inline scripts)

x.yml 
lint: npm run lint

build: |
  VERSION="$1"
  npm run build
  npm version "$VERSION"
  git push --tags

Extra CLI arguments after the command name become $1, $2, … in the script body.

Mapping entries (nested subcommands)

Nested commands 
deploy:
  $: |
    echo "Deploying (default)"
    x deploy dev
  dev: npm run deploy:dev
  prod: npm run deploy:prod
  test:
    unit: npx jest unit
    integration: npx jest integration
  • $: default handler when you run the parent with no further arguments (x deploy).
  • Any other key: nested subcommand; mappings can nest arbitrarily deep.
  • x deploy prod → deploy.prod
  • x deploy test unit → deploy.test.unit
Note: If a mapping has nested keys but no $ handler, invoking the parent alone (e.g. x deploy) produces an error asking you to add $ or pass a subcommand.

Execution details

Local scripts use your configured default program (x --config → default_program in ~/.x.sh/config.json), typically bash. No per-entry metadata is supported.

Activity tracking

Runs from x.yml are not recorded in x --ls activity data; only global scripts are tracked.

Apps
Overview

Apps turn a single <name>.x.yml file into a structured CLI with options, positional arguments, nested subcommands, and bash handlers. Unlike x.yml inline scripts, apps get parse-time validation: x checks required args, defaults, choice membership, requires: chains, and unknown flags before any handler bash executes.

Where apps live

  • Local: ./<name>.x.yml (discovered from CWD up through parents).
  • Global: ~/.x.sh/apps/<name>.x.yml.

Creating an app

x -i --app my-app             # prompts for local vs global
x -i --app --local my-app     # ./my-app.x.yml
x -i --app --global my-app    # ~/.x.sh/apps/my-app.x.yml

After the editor closes, x validates the YAML structure, parses every synopsis string, and checks handler coverage. On failure you can edit (re-open) or revert (restore prior file or delete the new one).

App vs project-local

Feature x.yml App (<name>.x.yml)
Scope CWD only CWD + parent walk / global
CLI parsing None (raw args as $1…) Full synopsis DSL + validation
Options / flags No Yes
Help generation No Auto -h / --help per command
Handlers Inline YAML strings Bash in $: block or $.import
Metadata None name, version, description

Handler imports

Large apps can split handlers into external YAML files via $.import. This is mutually exclusive with an inline $: block.

$.import:
  - ./handlers/build.yml
  - ./handlers/deploy.yml
File Format
<app>.x.yml 
# metadata
name: my-app
version: 0.0.0
description: an example app

options:
  - "[-v | --version]"

commands:
  build:
    description: build the project
    options:
      - "[--input=<file> [--output=<dir>]]"
      - "[--mode={fast|safe|deep}]"
    arguments:
      - "<assets>..."

  create:
    description: create things
    commands:
      file:
        description: create a file
        arguments: "<path> [<content='empty'>]"
      folder:
        arguments: "<path>"

$:
  build: |
    echo "mode=$(x-opt mode), assets=$(x-arg assets)"
  create: x-usage create
  create.file: |
    echo "creating $(x-arg path) with $(x-arg content)"
  create.folder: |
    mkdir -p "$(x-arg path)"

Top-level fields

  • name, version, description: metadata shown in help output.
  • options: flags available on the root command.
  • arguments: positional args on the root command.
  • commands: nested subcommand tree.
  • $ or $.import: bash handler map (mutually exclusive).

Command nodes

Each entry under commands can have description, options, arguments, nested commands, or any combination. Leaf commands need a matching handler key in $ (e.g. build → $: build:).

Non-leaf groups

A command with subcommands but no direct handler can use a one-liner like create: x-usage create to print help when invoked without a subcommand.

Imported handlers

External files referenced by $.import have the same flat dotted.path: bash body shape as the inline $: block.

Synopsis DSL

Every string in options and arguments arrays is a synopsis that x parses into a structured CLI spec. All constraints are enforced before handlers run.

All [optional] forms have bare (required) equivalents

Arguments

Synopsis Meaning Example
<name> Required positional x app file.txt
[<name>] Optional positional x app or x app file.txt
[<name='val'>] Optional with default x app or x app myfile.txt
<name>... Required repeating x app f1.txt f2.txt
[<name>...] Optional repeating x app or x app f1.txt f2.txt
<name={a|b|c}> Required, value from set x app write
[<name={a|b|c}>] Optional, value from set x app or x app fast
(a|b|c) Required choice (positional choice) x app north

Options

Synopsis Meaning Example
--long Required bool flag x app --long
(-l | --long) Required bool, alias pair x app -l
(--long | --short) Required mutually exclusive x app --long or x app --short
(-l | --long | -s | --short) Required mutex with aliases x app -l or x app -s
[-l | --long] Optional bool flag x app -l
[-l | --long <arg>] Flag with required value x app -l ./dist
[-l | --long <arg='v'>] Flag with default value x app or x app --long ./dist
[-l | --long <arg> ...] Value repeats x app --long "a" "b"
[-l | --long <arg>]... Flag repeats x app --long abc --long xyz
[--long=<arg>] Value via = x app --long=./dist
[--long=<arg='v'>] = form with default x app or x app --long=./dist
[--long={a|b|c}] Value from set x app --long=a
[--input=<a> [--output=<b>]] --output requires --input x app --input=foo --output=bar

Validation guarantees

  • Required arguments and options must be present.
  • Defaults are applied when optional values are omitted.
  • Choice values must be members of the declared set.
  • requires: chains from nested bracket groups are enforced.
  • Mutually exclusive option groups require exactly one member.
  • Repeating positionals must be the last argument in the list.
  • Unknown options are rejected with a clear error.

YAML anchors

Standard YAML anchors and aliases work for sharing option sets across commands. See the example app for &demo_verbose / *demo_verbose usage.

Built-in Helpers

x prepends a small bash preamble to each handler so you can read parsed values without manual environment-variable wrangling. All helpers are available in the handler's scope and exported for x-run subprocesses.

Builtin Behavior
x-opt <name> Print option value. Bool flags → true. Repeats join with newline.
x-arg <name> Print positional argument value.
x-opts <assoc-name> Populate a caller-named bash associative array with all options.
x-args <assoc-name> Populate a caller-named bash associative array with all arguments.
x-run <cmd> [args…] Run a command with x-* helpers still in scope.
x-usage <cmd-path> Print auto-generated help (e.g. x-usage create.file).
x-io-read … Prompt for a line. -v / --var assigns to a global scalar.
x-io-confirm … Yes/no prompt (--default yes|no). -v assigns true/false.
x-io-select … Menu of id=label pairs. --multi for multiple. -v assigns result.
x-prt … Styled print via ANSI SGR. (-s|--style) <style> sets comma-separated styles; sticky until next --style.
x-tui … Terminal control via ANSI escapes (--init, --exit, --clear, cursor moves, etc.).

Reading options and arguments

echo "mode=$(x-opt mode)"
echo "path=$(x-arg path)"

declare -A opts
x-opts opts
echo "${opts[mode]}"

declare -A args
x-args args
for k in "${!args[@]}"; do echo "$k=${args[$k]}"; done

Repeating options

mapfile -t dirs < <(x-opt dir)
for d in "${dirs[@]}"; do echo "dir: $d"; done

Interactive I/O

x-io-read "Name:" -v name
echo "$name"

x-io-confirm "Proceed?" --default no -v ok
[[ "$ok" == "true" ]] && echo "go"

x-io-select -v color "Pick a color" "red=Red" "green=Green" "blue=Blue"
echo "$color"

x-io-select --multi -v colors "Colors" "r=Red" "g=Green"
echo "${colors[0]}"
Tip: With -v / --var, results land in the caller's global shell variable, not stdout. Multi-select stores an indexed array.
Validation & Help

Automatic help

Every command supports -h / --help out of the box, with no extra configuration.

x my-app --help
x my-app build --help
x my-app create file --help

The same renderer powers x-usage <cmd-path> inside handlers, so you can print context-appropriate help from bash.

Save-time validation (x -i --app)

When you finish editing an app file, x performs a full structural check:

  • YAML parses cleanly.
  • Every synopsis string parses into a valid spec.
  • Leaf commands have corresponding $ handlers.
  • No orphan handler keys.
  • No duplicate options within a command.
  • No dangling requires: references.
  • $ and $.import are not both present.

On failure, x lists all errors and offers edit (re-open the editor) or revert.

Runtime validation

A lighter validation pass runs on every x <app> invocation so hand-edited or stale files fail fast with readable errors before any bash executes.

Examples

Comprehensive example app (exapp)

The app definition imports handlers from two sidecar files:

exapp.x.yml 
# Comprehensive sample app for the `x` app framework (`x exapp …`).
# Demonstrates: metadata, root options/arguments, nested commands, YAML anchors,
# every synopsis form from the cheat-sheet, and split `$.import` handler files.

name: exapp
version: 0.1.0
description: >-
  Exercise app: exercises options, positionals, nesting, validation,
  `$.import`, and bash helpers (`x-opt`, `x-arg`, `x-opts`, `x-args`, `x-run`, `x-usage`).

options:
  - "[-v | --version]"
  - "[-g | --global <note=''>]"

arguments:
  - "[<topic='overview'>]"

commands:
  demo:
    description: nested demos (each subcommand highlights different DSL pieces)

    commands:
      opts:
        description: >-
          Option forms: bool pair, value, defaulted value, repeating values,
          enum choice, `=` default, requires-chain, and a required bare flag.
        options:
          - "[-n | --dry-run]"
          - "[-o | --out <path>]"
          - "[-c | --count <n='1'>]"
          - "[-D | --define <kv> ...]"
          - "[--kind={alpha|beta|gamma}]"
          - "[--label=<text='demo'>]"
          - "[--src=<path> [--dst=<path>]]"
          - "[--default={yes|no}]"
          - "--commit"
          - "(-f | --force)"
          - "(--fmt | --format)"
          - "(-q | --quiet | -v | --verbose)"
          - "[--tag <label>]..."

      args:
        description: >-
          Positional forms: required, optional, optional-with-default,
          and greedy repeat (must be last).
        arguments:
          - "<one> [<two>] [<three='3'>] [<rest>...]"

      pick:
        description: required choice; `(alt1|alt2|alt3)` becomes positional name `choice`
        arguments:
          - "(north|south|east|west)"

      mode:
        description: positional choice in angle brackets
        arguments:
          - "<action={read|write|delete}> [<speed={fast|slow}='fast'>]"

      tail:
        description: optional repeating positional `[<items>...]`
        arguments:
          - "[<items>...]"

      group:
        description: >-
          Non-leaf group: invoke `x exapp demo group` with no subcommand to see auto-help.
        commands:
          alpha:
            description: nested leaf α; shares options via YAML anchor (see `reflect`)
            options: &demo_verbose
              - "[-V | --verbose]"
            arguments:
              - "<msg>"
          beta:
            description: nested leaf β, with the same shared options as `alpha`
            options: *demo_verbose
            arguments:
              - "<msg>"

      reflect:
        description: dump parsed options/args via `x-opts` / `x-args` (and `x-run`)
        options: *demo_verbose
        arguments:
          - "[<label='state'>]"

      sparse:
        description: optional repeat with a default (see also `tail` for plain `[<items>...]`)
        arguments:
          - "[<parts='*'>...]"

      usage-tip:
        description: >-
          One-line handler that forwards to x-usage (same idea as README create → x-usage create).

      io:
        description: interactive builtins
        commands:
          read:
            description: read a line of text
          confirm:
            description: confirm a yes/no question
          select:
            description: select an option from a list
          multiselect:
            description: select an option from a list

$.import:
  - ./exapp.handlers-a.yml
  - ./exapp.handlers-b.yml
exapp.handlers-a.yml 
# Handlers merged via `$.import` (first file). Keys are dotted command paths.

"":
  |
    topic=$(x-arg topic)
    note=$(x-opt global)
    echo "exapp: topic=${topic:-overview}  global-note=${note:-∅}"
    echo "Try:  x exapp --help"
    echo "       x exapp demo --help"

demo.opts:
  |
    echo "dry-run=$(x-opt dry-run)"
    echo "out=$(x-opt out)"
    echo "count=$(x-opt count)"
    mapfile -t defs < <(x-opt define)
    printf 'define[%s]\n' "${defs[@]:-}"
    echo "kind=$(x-opt kind)"
    echo "label=$(x-opt label)"
    echo "src=$(x-opt src)"
    echo "dst=$(x-opt dst)"
    echo "commit=$(x-opt commit)"

demo.args:
  |
    echo "one=$(x-arg one)"
    echo "two=$(x-arg two)"
    echo "three=$(x-arg three)"
    mapfile -t rest < <(x-arg rest)
    printf 'rest[%s]\n' "${rest[@]:-}"

demo.pick:
  |
    echo "direction=$(x-arg choice)"

demo.tail:
  |
    mapfile -t items < <(x-arg items)
    if ((${#items[@]})); then
      printf 'items: %s\n' "${items[@]}"
    else
      echo "(no items)"
    fi

  |
    mapfile -t parts < <(x-arg parts)

demo.usage-tip: x-usage demo.opts

  |

demo.reflect:
  |
    declare -A opts args
    x-opts opts
    x-args args
    echo "--- x-opts ($(x-arg label)) ---"
    for k in "${!opts[@]}"; do echo "  $k=${opts[$k]}"; done | sort

    for k in "${!args[@]}"; do echo "  $k=${args[$k]}"; done | sort
    echo "--- x-run ---"
    x-run echo "ran nested echo via x-run"

  fi

  echo "Submit = $answer"

  echo "Delete = $answer"

Typical workflows

  • Dotfiles scripts: x -i for personal utilities, x --ln for PATH access.
  • Monorepo tasks: root x.yml for build, test, lint; no global install needed.
  • Team CLI tool: commit <tool>.x.yml to the repo; teammates run x tool subcmd from any subdirectory.
  • Complex internal CLI: global app in ~/.x.sh/apps/ with $.import for large handler sets.
Configuration

x --config

Interactive menu with two options:

Default Script Language

Sets default_program in ~/.x.sh/config.json. Pre-selected during x -i and used for x.yml inline execution.

LLM Provider

Opens your editor with a template script saved to ~/.x.sh/config/llm.sh. The script must accept the prompt as $1 and print the completion to stdout.

FAQs
Why does x my-script not find my x.yml entry?

x.yml is only read from the current working directory, not parent directories. cd to the directory containing x.yml, or use a global script / app instead.

Why does a local app work from a subdirectory but x.yml does not?

By design. Apps walk up the directory tree; x.yml does not. Put shared project commands in a root-level app or keep x.yml usage to single-directory workflows.

x --ln created a symlink but the command is not found

Ensure ~/.local/bin is on your PATH. Run echo $PATH and verify. You may need to open a new shell after updating your rc file.

My app fails validation after editing

Run x -i --app --local <name> (or --global) to re-enter the edit/revert loop. Common issues: missing handler for a leaf command, invalid synopsis syntax, or both $ and $.import present.

Can I use extensions in script names?

Script names you pass to x are extensionless (e.g. x c-test). The file on disk can include an extension (c-test.c); x resolves by basename match.

Does x --delete remove symlinks?

No. Use x -d --ln <name> to remove symlinks separately.
