x.sh

Apps>Project-local Scripts

Place a file named x.yml in your current working directory. When you run x <name>, x loads it and looks for a top-level command matching <name>. If found, the command runs; otherwise x falls back to an app or global script.

v3: x.yml uses exactly the same file format as app files (see App File Format) - the only difference is that it's invoked without a name prefix, and name: is never required.
Warning: Only the CWD is checked for x.yml, not parent directories. Invalid YAML (or removed v3 syntax like commands:) fails immediately; x does not fall back to global scripts on parse/validation errors.

Dot-prefixed commands

Every command is declared with a .command-name: key. The value is either:

  • A string - shorthand for an inline script (equivalent to { $: <string> }). Often a block scalar with |.
  • A mapping - any of description/help, options/opts, arguments/args, dir, env, alias, its own $: script, and nested .sub-command: keys.
x.yml 
.lint: npm run lint

.build:
  args: <version>
  $: |
    npm run build
    npm version "$(x-arg version)"
    git push --tags

.deploy:
  $: |
    echo "Deploying (default)"
    x deploy dev
  .dev: npm run deploy:dev
  .prod: npm run deploy:prod
  .test:
    .unit: npx jest unit
    .integration: npx jest integration
  • x build 1.2.3 → x-arg version is 1.2.3 (or, without a declared synopsis, extra CLI arguments become $1, $2, … in the script body).
  • x deploy → runs deploy's own $.
  • x deploy prod → runs deploy.prod.
  • x deploy test unit → runs deploy.test.unit.
Note: If a command has subcommands but no $: of its own, invoking it bare (e.g. x deploy when only nested .dev/.prod/.test exist) auto-prints help instead of erroring.

Execution details

Local commands always run as bash, with the same x-opt/x-arg/x-usage preamble injected before every app script. Unlike global scripts (which respect default_program / per-script metadata), x.yml and app commands are bash-only. No per-entry metadata is supported.

Activity tracking

Runs from x.yml are not recorded in x --ls activity data; only global scripts are tracked.
