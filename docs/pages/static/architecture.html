x.sh

Architecture

Command resolution flow

When you invoke x <name> [args…], x walks a fixed resolution chain. The first match wins and the process exits after execution.

Local app discovery

Unlike x.yml (current directory only), local apps are discovered by walking from the current working directory up through every parent directory. The nearest <name>.x.yml wins. This lets monorepos keep a shared app at the repo root while you work in subdirectories.

Global script lookup

Scripts in ~/.x.sh/scripts/ are matched by exact filename first, then by basename without extension, so x c-test finds c-test.c automatically.

Metadata model

Each global script can have a companion TOML file at ~/.x.sh/metadata/<name>.toml:

description = "Fetch a URL with curl"
groups = ["network", "utils"]
program = "bash

Activity data (created, updated, last_executed) is stored separately in ~/.x.sh/metadata.json and shown in x --ls.

Inline script execution

Project-local x.yml entries and certain inline paths run via your configured default program (typically bash):

<program> -c '<script body>' x <remaining-args…>

Positional parameters in the script body ($1, $2, …) refer to arguments after the command name.

Script/App Resolution Order

When you run x <name> [args…], x walks a fixed resolution chain. The first match will be executed.

  1. ./x.yml → a top-level command named <name> (CWD only)
  2. ./<name>.x.yml → local app (CWD, then parent dirs)
  3. ~/.x.sh/apps/ → global app
  4. ~/.x.sh/scripts/ → installed global script

x.yml and <name>.x.yml apps run through the exact same engine (parsing, validation, subcommands, $: scripts) - see Project-local Scripts and File Format.
