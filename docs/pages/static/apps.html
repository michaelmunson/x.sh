x.sh

Overview

Apps turn a single <name>.x.yml file into a structured CLI with options, positional arguments, nested .command: keys, and per-command $: scripts. Apps get parse-time validation: x checks required args, defaults, choice membership, requires: chains, and unknown flags before any script executes. Project-local x.yml files (see Project-local Scripts) use this exact same file format — just invoked without a name prefix.

Where apps live

  • Local: ./<name>.x.yml (discovered from CWD up through parents).
  • Global: ~/.x.sh/apps/<name>.x.yml.

Creating an app

x -i --app my-app             # prompts for local vs global
x -i --app --local my-app     # ./my-app.x.yml
x -i --app --global my-app    # ~/.x.sh/apps/my-app.x.yml

After the editor closes, x validates the YAML structure, parses every synopsis string, and checks handler coverage. On failure you can edit (re-open) or revert (restore prior file or delete the new one).

App vs project-local

As of v3, x.yml and apps run on the same engine — full synopsis DSL, validation, nested .command: keys, and auto-help all work in both. The differences are only about scope and invocation:

Feature x.yml App (<name>.x.yml)
Scope CWD only CWD + parent walk / global
Invocation x <command> (no name prefix) x <name> <command>
CLI parsing Full synopsis DSL + validation Full synopsis DSL + validation
Options / flags Yes Yes
Help generation Auto -h / --help per command Auto -h / --help per command
Scripts Inline $: per command, or import.$ Inline $: per command, or import.$
Metadata name: optional (never shown with a prefix) name, version, description shown in help

Handler imports

Large files can split scripts into external YAML files via import.$ (or the legacy $.import). This is mutually exclusive with an inline top-level $: handler map — which no longer exists in v3 anyway; imports simply supply scripts for commands that don't declare their own inline $:.

import:
  $:
    - ./handlers/build.yml
    - ./handlers/deploy.yml

Legacy form (still supported, mutually exclusive with import.$):

$.import:
  - ./handlers/build.yml
  - ./handlers/deploy.yml

File Format

This is the same file format used by project-local x.yml files — see Project-local Scripts. Commands are declared with dot-prefixed keys (.command-name:), never commands:.

<app>.x.yml 
# metadata
name: my-app
version: 0.0.0
description: an example app

options:
  - "[-v | --version]"

.build:
  description: build the project
  options:
    - "[--input=<file> [--output=<dir>]]"
    - "[--mode={fast|safe|deep}]"
  arguments:
    - "<assets>..."
  $: |
    echo "mode=$(x-opt mode), assets=$(x-arg assets)"

.create:
  description: create things
  $: x-usage create

  .file:
    description: create a file
    arguments: "<path> [<content='empty'>]"
    $: |
      echo "creating $(x-arg path) with $(x-arg content)"

  .folder:
    arguments: "<path>"
    $: |
      mkdir -p "$(x-arg path)"

Top-level fields

  • name: app name; defaults to the filename without .x.yml/.yml if omitted.
  • version, description/help: metadata shown in help output (help/description are aliases — pick one).
  • options/opts, arguments/args: root command synopsis (aliases; string, multiline string, or list).
  • dir: working directory scripts run in (relative to the app file, or absolute).
  • env: inline environment variables and named groups.
  • import: unified imports — $ (script files), env (.env files), sh (scripts to source).
  • $: the root command's own inline script, run on bare x my-app.
  • .command-name: a subcommand — a string (shorthand inline script) or a mapping.
Removed in v3: the commands: mapping and a top-level $: handler map are both gone. Define commands with .command-name: keys, and put each command's script inline under its own $:.

Command nodes

Each .command-name: entry is either a string (shorthand for { $: <string> }) or a mapping with any of description/help, options/opts, arguments/args, dir, env, alias, $, and nested .sub-command: keys. Every leaf command needs its own $: (or alias:).

.docs: cargo doc --no-deps    # shorthand — equivalent to { $: cargo doc --no-deps }

Non-leaf groups

A command with subcommands but no $: of its own auto-prints help when invoked bare. To customize that, give it its own $: — a one-liner like x-usage create prints the same generated help explicitly.

Working directory (dir)

Set dir to change the process working directory before a script runs. Relative paths resolve from the directory containing the app file; absolute paths are used as-is. The directory must exist at load time. dir set on a command applies to that command and all its subcommands, unless a subcommand sets its own.

name: my-app
dir: ./app

.show:
  description: print the handler working directory
  $: |
    pwd

With the app file at ./my-app.x.yml and a subdirectory ./app/, running x my-app show executes the script with ./app as the current working directory.

Alias commands

An alias: command dispatches its remaining arguments to another x file, as if you'd invoked that file directly. Alias commands may define only alias and help/description — no options, arguments, dir, env, $, or nested commands.

.legacy:
  alias: ./tools/legacy.x.yml

x my-app legacy <rest…> runs <rest…> against legacy.x.yml as if you'd run it directly (as its own root command).

Multiline opts/args shorthand

opts/options and args/arguments accept a single multiline string as an alternative to a YAML list — each non-empty line becomes one synopsis fragment:

opts: |
  [-n | --dry-run]
  [-o | --out <path>]
  --commit

is equivalent to:

options:
  - "[-n | --dry-run]"
  - "[-o | --out <path>]"
  - "--commit"

Imports

Split scripts into sidecar files instead of inline $: entries. Each import file is a flat YAML map of dotted.path: <bash body> — the same shape used before v3, and these files are not rewritten to dot-prefixed keys. Paths resolve relative to the app file. Duplicate keys across import files are an error; inline $: entries override imported scripts with the same key.

name: my-app
version: 0.0.0

.greet:
  arguments: "<name>"

import:
  $:
    - ./handlers.yml
handlers.yml 
greet: |
  echo "Hello, $(x-arg name)"

Legacy form (still supported, mutually exclusive with import.$):

"$.import":
  - ./handlers.yml

Environment

Inline env: defines globals available before scripts run. Named groups (keys starting with .) are loaded on demand via x-env-load. You can also import a classic .env file through import.env. Like dir, env set on a command merges downward to its subcommands (its own values win, but parent env vars not overridden still apply).

name: my-app
version: 0.0.0

env:
  HELLO: "world"
  .production:
    API_URL: https://example.com

.deploy:
  arguments: "<target>"
  $: |
    x-env-load ".$(x-arg target)"
    echo "$HELLO → $API_URL"

import:
  env: ./shared.env
  sh:
    - ./helpers/example.sh
    - ./helpers/example2.sh
  $:
    - ./handlers/deploy.yml
shared.env 
DATABASE_URL=postgres://localhost/mydb
LOG_LEVEL=info

Imported .env globals merge first; inline env: values override on duplicate keys.

Synopsis DSL

Every string in options/opts and arguments/args is a synopsis that x parses into a structured CLI spec. These fields accept a list of strings, a single string, or a multiline string (one fragment per line) — all three forms are equivalent. All constraints are enforced before scripts run.

All [optional] forms have bare (required) equivalents

Multiline opts (equivalent to a list) 
opts: |
  [-n | --dry-run]
  [-o | --out <path>]
  --commit

Arguments

Synopsis Meaning Example
<name> Required positional x app file.txt
[<name>] Optional positional x app or x app file.txt
[<name='val'>] Optional with default x app or x app myfile.txt
<name>... Required repeating x app f1.txt f2.txt
[<name>...] Optional repeating x app or x app f1.txt f2.txt
<name={a|b|c}> Required, value from set x app write
[<name={a|b|c}>] Optional, value from set x app or x app fast
(a|b|c) Required choice (positional choice) x app north

Options

Synopsis Meaning Example
--long Required bool flag x app --long
(-l | --long) Required bool, alias pair x app -l
(--long | --short) Required mutually exclusive x app --long or x app --short
(-l | --long | -s | --short) Required mutex with aliases x app -l or x app -s
[-l | --long] Optional bool flag x app -l
[-l | --long <arg>] Flag with required value x app -l ./dist
[-l | --long <arg='v'>] Flag with default value x app or x app --long ./dist
[-l | --long <arg> ...] Value repeats x app --long "a" "b"
[-l | --long <arg>]... Flag repeats x app --long abc --long xyz
[--long=<arg>] Value via = x app --long=./dist
[--long=<arg='v'>] = form with default x app or x app --long=./dist
[--long={a|b|c}] Value from set x app --long=a
[--input=<a> [--output=<b>]] --output requires --input x app --input=foo --output=bar

Validation guarantees

  • Required arguments and options must be present.
  • Defaults are applied when optional values are omitted.
  • Choice values must be members of the declared set.
  • requires: chains from nested bracket groups are enforced.
  • Mutually exclusive option groups require exactly one member.
  • Repeating positionals must be the last argument in the list.
  • Unknown options are rejected with a clear error.

YAML tips

  • Quote synopsis strings that start with [ or contain { to avoid YAML parsing issues.
  • Standard YAML anchors and aliases work for sharing option sets across commands. See the example app for &demo_verbose / *demo_verbose usage.
  • args/arguments may be a single string: args: "<path> [<content='empty'>]".

Built-in Helpers

x prepends a small bash preamble to each handler so you can read parsed values without manual environment-variable wrangling. All helpers are available in the handler's scope and exported for x-run subprocesses.

Builtin Behavior
x-opt <name> Print option value. Bool flags → true. Repeats join with newline.
x-arg <name> Print positional argument value.
x-opts <assoc-name> Populate a caller-named bash associative array with all options.
x-args <assoc-name> Populate a caller-named bash associative array with all arguments.
x-run <cmd> [args…] Run a command with x-* helpers still in scope.
x-usage <cmd-path> Print auto-generated help (e.g. x-usage create.file).
x-io-read … Prompt for a line. -v / --var assigns to a global scalar.
x-io-confirm … Yes/no prompt (--default yes|no). -v assigns true/false.
x-io-select … Menu of id=label pairs. --multi for multiple. -v assigns result.
x-prt … Styled print via ANSI SGR. (-s|--style) <style> sets comma-separated styles; sticky until next --style.
x-tui … Terminal control via ANSI escapes (--init, --exit, --clear, cursor moves, etc.).
x-env-load .<group> Export variables from a named env: group (e.g. x-env-load .env1). Global env: vars are already in the shell before the script runs.
x-path-root Print the absolute path of the directory containing the x file (app or x.yml).
Env vars: parsed values are also available directly as environment variables — X_OPT_<name>, X_ARG_<name> (hyphens → underscores), X_OPTS_PAIRS, X_ARGS_PAIRS, X_BIN, X_APP, X_APP_FILE.

Reading options and arguments

echo "mode=$(x-opt mode)"
echo "path=$(x-arg path)"

declare -A opts
x-opts opts
echo "${opts[mode]}"

declare -A args
x-args args
for k in "${!args[@]}"; do echo "$k=${args[$k]}"; done

Repeating options

mapfile -t dirs < <(x-opt dir)
for d in "${dirs[@]}"; do echo "dir: $d"; done

Interactive I/O

x-io-read "Name:" -v name
echo "$name"

x-io-confirm "Proceed?" --default no -v ok
[[ "$ok" == "true" ]] && echo "go"

x-io-select -v color "Pick a color" "red=Red" "green=Green" "blue=Blue"
echo "$color"

x-io-select --multi -v colors "Colors" "r=Red" "g=Green"
echo "${colors[0]}"
Tip: With -v / --var, results land in the caller's global shell variable, not stdout. Multi-select stores an indexed array.

Validation & Help

Automatic help

Every command supports -h / --help out of the box, with no extra configuration.

x my-app --help
x my-app build --help
x my-app create file --help

Non-leaf commands without their own $: auto-print help when invoked bare. The same renderer powers x-usage <cmd-path> inside scripts, so you can print context-appropriate help from bash.

Save-time validation (x -i --app)

When you finish editing an app file, x performs a full structural check:

  • YAML parses cleanly.
  • Removed v3 syntax: a commands: mapping, or a top-level $: used as a handler map.
  • Every synopsis string parses into a valid spec.
  • Leaf commands have a $: script or an alias:.
  • Script keys (inline or imported) match a defined command path.
  • alias: commands don't also define options/arguments/dir/env/$/subcommands.
  • No duplicate options or arguments within a command.
  • No dangling requires: references.
  • No conflicting help/description, options/opts, or arguments/args on the same node.
  • $.import and import.$ are not both present.

On failure, x lists all errors and offers edit (re-open the editor) or revert.

Runtime validation

A lighter validation pass runs on every x <app> / project x.yml invocation so hand-edited or stale files fail fast with readable errors before any bash executes.

Examples

Comprehensive example app (exapp)

The app definition imports scripts from two sidecar files via import.$:

exapp.x.yml 
# Comprehensive sample app for the `x` app framework (`x exapp …`).
# Demonstrates: metadata, root options/arguments, nested commands, YAML anchors,
# every synopsis form from the cheat-sheet, and split `import.$` handler files.

name: exapp
version: 0.1.0
description: >-
  Exercise app — exercises options, positionals, nesting, validation, and bash helpers
  (`x-opt`, `x-arg`, `x-opts`, `x-args`, `x-run`, `x-usage`).
import:
  $:
    - handlers/exapp.handlers-a.yml
    - handlers/exapp.handlers-b.yml
env:
  DEBUG: "true"

options:
  - '[-v | --version]'
  - '[-g | --global <note="">]'

arguments: '[<topic="overview">]'

.demo:
  description: nested demos (each subcommand highlights different DSL pieces)

  .opts:
    description: >-
      Option forms — bool pair, value, defaulted value, repeating values,
      enum choice, `=` default, requires-chain, and a required bare flag.
    opts: |
      [-n | --dry-run]
      [-o | --out <path>]
      [-c | --count <n="1">]
      [-D | --define <kv> ...]
      [--kind={alpha|beta|gamma}]
      [--label=<text="demo">]
      [--src=<path> [--dst=<path>]]
      [--default={yes|no}]
      --commit
      (-f | --force)
      (--fmt | --format)
      (-q | --quiet | -v | --verbose)
      [--tag <label>]...

  .args:
    description: >-
      Positional forms — required, optional, optional-with-default,
      and greedy repeat (must be last).
    args: '<one> [<two>] [<three="3">] [<rest>...]'

  .pick:
    description: required choice — `(alt1|alt2|alt3)` becomes positional name `choice`
    args: '(north|south|east|west)'

  .mode:
    description: >-
      Positional choice in angle brackets — `<action={…}>` and
      optional `[<speed={…}='default'>]`.
    args: '<action={read|write|delete}> [<speed={fast|slow}="fast">]'

  .tail:
    description: optional repeating positional `[<items>...]`
    args: '[<items>...]'

  .group:
    description: >-
      Non-leaf group — invoke `x exapp demo group` with no subcommand to see auto-help.
    .alpha:
      description: nested leaf α — shares options via YAML anchor (see `reflect`)
      opts: &demo_verbose
        - '[-V | --verbose]'
      args: '<msg>'
    .beta:
      description: nested leaf β — same shared options as `alpha`
      opts: *demo_verbose
      args: '<msg>'

  .reflect:
    description: dump parsed options/args via `x-opts` / `x-args` (and `x-run`)
    opts: *demo_verbose
    args: '[<label="state">]'

  .sparse:
    description: optional repeat with a default (see also `tail` for plain `[<items>...]`)
    args: '[<parts="*">...]'

  .usage-tip:
    description: >-
      One-line handler — forwards to x-usage (same idea as README create → x-usage create).

  .io:
    description: interactive builtins
    .read:
      description: read a line of text
    .confirm:
      description: confirm a yes/no question
    .select:
      description: select an option from a list
    .multiselect:
      description: select an option from a list

  .style:
    description: terminal styling and TUI control builtins
    .prt:
      description: styled print via x-prt (--style)
    .tui:
      description: alternate buffer demo via x-tui

.debug:
  description: debug the environment variables
  $: |
    echo "DEBUG = $DEBUG"
handlers/exapp.handlers-a.yml 
# Scripts merged via `import.$` (first file). Keys are dotted command paths —
# import files keep this flat shape; they're not rewritten to dot-prefixed keys.

"":
  |
    topic=$(x-arg topic)
    note=$(x-opt global)
    echo "exapp — topic=${topic:-overview}  global-note=${note:-∅}"
    echo "Try:  x exapp --help"
    echo "       x exapp demo --help"

demo.opts:
  |
    echo "dry-run=$(x-opt dry-run)"
    echo "out=$(x-opt out)"
    echo "count=$(x-opt count)"
    mapfile -t defs < <(x-opt define)
    printf 'define[%s]\n' "${defs[@]:-}"
    echo "kind=$(x-opt kind)"
    echo "label=$(x-opt label)"
    echo "src=$(x-opt src)"
    echo "dst=$(x-opt dst)"
    echo "commit=$(x-opt commit)"
    echo "force=$(x-opt force)"
    echo "fmt=$(x-opt fmt)"
    echo "format=$(x-opt format)"
    echo "quiet=$(x-opt quiet)"
    echo "verbose=$(x-opt verbose)"
    mapfile -t tags < <(x-opt tag)
    printf 'tag[%s]\n' "${tags[@]:-}"

demo.mode:
  |
    echo "action=$(x-arg action)"
    echo "speed=$(x-arg speed)"

demo.args:
  |
    echo "one=$(x-arg one)"
    echo "two=$(x-arg two)"
    echo "three=$(x-arg three)"
    mapfile -t rest < <(x-arg rest)
    printf 'rest[%s]\n' "${rest[@]:-}"

demo.pick:
  |
    echo "direction=$(x-arg choice)"

demo.tail:
  |
    mapfile -t items < <(x-arg items)
    if ((${#items[@]})); then
      printf 'items: %s\n' "${items[@]}"
    else
      echo "(no items)"
    fi

demo.sparse:
  |
    mapfile -t parts < <(x-arg parts)
    echo "parts=${parts[*]}"

demo.usage-tip: x-usage demo.opts
handlers/exapp.handlers-b.yml 
# Second import file — merged keys must not duplicate the first import.

demo.group.alpha:
  |
    msg=$(x-arg msg)
    if [[ $(x-opt verbose) == true ]]; then
      echo "[verbose] alpha ← $msg"
    else
      echo "alpha ← $msg"
    fi

demo.group.beta:
  |
    msg=$(x-arg msg)
    if [[ $(x-opt verbose) == true ]]; then
      echo "[verbose] beta ← $msg"
    else
      echo "beta ← $msg"
    fi

demo.reflect:
  |
    declare -A opts args
    x-opts opts
    x-args args
    echo "--- x-opts ($(x-arg label)) ---"
    for k in "${!opts[@]}"; do echo "  $k=${opts[$k]}"; done | sort
    echo "--- x-args ---"
    for k in "${!args[@]}"; do echo "  $k=${args[$k]}"; done | sort
    echo "--- x-run ---"
    x-run echo "ran nested echo via x-run"

# IO commands
demo.io.read: |
  answer=$(x-io-read "What is your favorite color?")
  if [ "$answer" != "blue" ]; then
    echo "Wrong answer"
    exit 1
  else
    echo "Correct!"
  fi

demo.io.confirm: |
  answer=$(x-io-confirm "Are you sure you want to submit?" --default no)
  echo "Submit = $answer"
  answer=$(x-io-confirm "Are you sure you want to delete?" --default yes)
  echo "Delete = $answer"

demo.io.select: |
  x-io-select "Choose a color" \
    "red=Red" \
    "green=Green" \
    "blue=Blue" \
    "yellow/orange=Yellow or Orange" \
    -v color
  echo "Color = $color"

demo.io.multiselect: |
  x-io-select --multi "Choose a color" \
    "red=Red" \
    "green=Green" \
    "blue=Blue" \
    "yellow/orange=Yellow or Orange" \
    -v colors

  echo "First Color = ${colors[0]}"
  echo "All Colors = ${colors[*]}"

demo.style.prt: |
  x-prt \
    --style red,underline,bg-white \
    "Hello" \
    --style blue,bg-yellow \
    " World" \
    --newline
  x-prt --style green,bold "exapp prt demo"
  x-prt --style red,bold " exapp prt demo (red)" --newline

demo.style.tui: |
  x-tui --init --clear
  x-tui --home
  x-prt --style green,bold "exapp TUI demo"
  x-io-select "Action" "stay=Stay" "go=Go" -v action
  echo "Action = $action"
  if [ "$action" = "go" ]; then
    echo "Going!"
    x-prt --style red,bold "Going!"
  else
    echo "Staying!"
    x-prt --style green,bold "Staying!"
    sleep 2
    x-run x exapp demo style tui
  fi
  sleep 2
  x-tui --exit

.test:
  description: test the environment variable

  $: |

Typical workflows

  • Dotfiles scripts: x -i for personal utilities, x --ln for PATH access.
  • Monorepo tasks: root x.yml with .build, .test, .lint commands; no global install needed.
  • Team CLI tool: commit <tool>.x.yml to the repo; teammates run x tool subcmd from any subdirectory.
  • Complex internal CLI: global app in ~/.x.sh/apps/ with import.$ for large script sets.

Project-local Scripts

Place a file named x.yml in your current working directory. When you run x <name>, x loads it and looks for a top-level command matching <name>. If found, the command runs; otherwise x falls back to an app or global script.

v3: x.yml uses exactly the same file format as app files (see App File Format) — the only difference is that it's invoked without a name prefix, and name: is never required.
Warning: Only the CWD is checked for x.yml, not parent directories. Invalid YAML (or removed v3 syntax like commands:) fails immediately; x does not fall back to global scripts on parse/validation errors.

Dot-prefixed commands

Every command is declared with a .command-name: key. The value is either:

  • A string — shorthand for an inline script (equivalent to { $: <string> }). Often a block scalar with |.
  • A mapping — any of description/help, options/opts, arguments/args, dir, env, alias, its own $: script, and nested .sub-command: keys.
x.yml 
.lint: npm run lint

.build:
  args: <version>
  $: |
    npm run build
    npm version "$(x-arg version)"
    git push --tags

.deploy:
  $: |
    echo "Deploying (default)"
    x deploy dev
  .dev: npm run deploy:dev
  .prod: npm run deploy:prod
  .test:
    .unit: npx jest unit
    .integration: npx jest integration
  • x build 1.2.3 → x-arg version is 1.2.3 (or, without a declared synopsis, extra CLI arguments become $1, $2, … in the script body).
  • x deploy → runs deploy's own $.
  • x deploy prod → runs deploy.prod.
  • x deploy test unit → runs deploy.test.unit.
Note: If a command has subcommands but no $: of its own, invoking it bare (e.g. x deploy when only nested .dev/.prod/.test exist) auto-prints help instead of erroring.

Execution details

Local commands always run as bash, with the same x-opt/x-arg/x-usage preamble injected before every app script. Unlike global scripts (which respect default_program / per-script metadata), x.yml and app commands are bash-only. No per-entry metadata is supported.

Activity tracking

Runs from x.yml are not recorded in x --ls activity data; only global scripts are tracked.
